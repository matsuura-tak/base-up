# pdm の手引き：Web の読み替え

app.json の stacks に web があるときに、SKILL.md と合わせて読みます。Job、機会のツリー、前提の確かめ方、AC、指標と撤退の考え方は SKILL.md のままです。
アプリのストアを前提にした所だけを、下のように読み替えます。

## 競合と代替を集める（作業の順番の2）
- App Store の検索の代わりに、WebSearch で Job の言葉を検索し、上位に出る Web サービスを3件以上選ぶ。同じ Job を解くアプリがあれば、それも競合に入れてよい。
- 不満は、サービスの口コミ（比較サイト、SNS、Q&A サイト、Product Hunt など）から、2件以上に出るものを引用と URL で書く。読めなかったものは「見ていない」と書く。
- 料金のページを開き、無料でどこまで使えるかを表に書く（Web は無料で試せる競合が多いため）。
- アプリ以外の代替（紙、標準のメモ、LINE、表計算、何もしない）は同じく1つ以上。

## 前提の確かめ方（作業の順番の5）
- 安い順に、机上調査、Takuma への質問か画面案（5分）、ステージングの URL を Takuma だけに見せる、機能フラグで一部の利用者にだけ出す。Web は配るのが速いので、作る前に「待ちリストのページ」や偽のドアのテストで関心を測ってよい（測ったことを利用者にだまさない形で）。

## 指標とイベント（作業の順番の10と11）
- 基準値がなければ「未計測（公開後14日で測る）」。App Store Connect の同業比較の代わりに、解析の道具の数字と、公開された業界の調査を参考値にし、出典に書く。
- ガードレールに、エラーの割合（ブラウザの JS のエラーと、500 の割合）と、Core Web Vitals（LCP、INP、CLS）の「良い」の割合を入れる。
- イベントごとに、App Store のプライバシー表示の区分の代わりに、Cookie や外部への送信に当たるか、同意が要るか、外部送信の公表に載せるかを書く。

## 見つけてもらう（ストアでの位置づけの代わり。product.md と metadata/web.md）
- 見つけてもらう道を決める：検索、SNS の共有、紹介、広告。主の道を1つ選び、理由を書く。
- 検索から来てほしい画面ごとに、ページのタイトル（全角30字前後）、説明（全角80〜120字）、狙う言葉を metadata/web.md に書く。確かめられない言い方（「世界一の」）をしない。
- 共有されたときの画像とタイトル（OGP）で、中心の Job が伝わるようにする。
- アクセシビリティの方針を公開するなら、metadata/accessibility.md に項目ごとに G3 の証拠のパスを書く。証拠のない項目を「対応する」にしない。
- 法務の文書（docs/support/）：プライバシーポリシー、利用規約に加え、要るときは外部送信の公表、有料なら特定商取引法の表示の草案を書く。どれも Takuma の承認が要る。
